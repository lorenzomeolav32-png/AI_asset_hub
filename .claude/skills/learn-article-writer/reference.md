# Reference: schema, file layout, house style, SEO

## Where files live

- Articles: `content/learn/<slug>.md` — one file per article, filename equals
  `slug`.
- The index page (`/learn`) and article page (`/learn/[slug]`) are generated by
  Velite from this folder automatically. You never need to touch `app/learn/`
  or register the article anywhere else.

## Frontmatter schema (from `velite.config.ts`, collection `learn`)

```yaml
slug: string          # required, matches filename, kebab-case
title: string          # required
summary: string        # required, 1-2 sentences, shown on the article card
kind: tutorial | explainer | comparison   # required, default "explainer" — no other values are valid today
tags: string[]         # optional, default []
date: YYYY-MM-DD        # required (ISO date)
updated: YYYY-MM-DD      # optional, only add when you materially revise later
author: string          # optional, default "AI Assets Directory"
```

`metadata` (reading time, word count) and `toc` are computed by Velite — never
write these by hand.

### `summary` is a card blurb, not a synopsis

The `ArticleCard` component renders `summary` directly under the title on the
`/learn` grid. Write it as the hook that gets someone to click, in your own
voice, not as "This article explains X." Look at the real examples:

> "The exact steps depend on your client, but the shape is the same: put the
> skill where the client looks for it, then confirm it loaded."

> "Both make an assistant more capable, but they solve different problems. One
> is know-how, the other is access, and you often use them together."

### `tags`

Only the first 3 show on the card. Put the most identifying tags first:
tool/topic name, then `tutorial`/`comparison`/`explainer`-adjacent tags like
`setup`, then a broader category (`ai-agents`, `basics`).

## House style (extracted from the real articles)

- Second person, plain declarative sentences. No filler intros, no "in this
  article we will explore."
- Open with the actual answer or the core distinction in the first sentence or
  two. The reader should get value before the first heading.
- Clear `##` (H2) sections, each with a short, specific title — not generic
  labels like "Overview" or "Conclusion."
- Prose paragraphs of 3-6 sentences. Bullet lists only for genuinely
  list-shaped things (prerequisites, a short set of options) — not as a crutch
  to avoid writing sentences.
- No em dashes (project-wide rule, enforced by the `humanizer` skill). No
  decorative emojis. No bold-mini-heading bullet lists ("**Speed:** it's
  fast.").
- End when the useful information ends. No forced "conclusion" or "in summary"
  section — the real articles just stop after the last practical point.

## SEO / GEO requirements (from `PRODUCT_PLAN.md` / `TECH_DESIGN.md`)

These matter because `/learn` articles are meant to be cited by both search and
LLM answer engines (ChatGPT, Perplexity, Google AI Overviews):

- Crisp, early **definitions** — state what the thing is before explaining
  nuance.
- Clear `H2`/`H3` structure so the article is easy to excerpt.
- **Comparison tables** are welcome for `comparison` articles when there are 3+
  clean dimensions to compare (setup, cost, speed, use case) — skip the table
  if the real comparison is only 2-3 short points; prose reads better then (see
  `claude-skills-vs-mcp-servers.md`, which uses no table).
- Factual, attributable content. Do not present an unverified claim as settled
  fact.
- Quality guardrail from `PRODUCT_PLAN.md`: every piece must add **original
  value** (a tested step, a specific caveat, an opinion) — never a bare
  restatement of what a README already says. Thin, generic AI summaries are
  explicitly what this project is trying to avoid (Google penalizes them, and
  so should you).

## Best-of / roundup requests

`TECH_DESIGN.md` mentions a `best-of` kind conceptually, but the live
`velite.config.ts` schema for `learn` only accepts
`tutorial | explainer | comparison` (default `explainer`). If the user asks for
a "Best X for Y" roundup:

1. Point out the schema gap.
2. Ask whether it should become:
   - a **Curated Collection** (`content/collections/`, a different schema:
     `title, slug, summary, items: assetRef[]` — an ordered list of existing
     asset slugs), which is the shape `PRODUCT_PLAN.md` actually designed for
     roundups, or
   - a genuine schema change (adding `best-of` to the `kind` enum in
     `velite.config.ts`), which is a code change outside this skill's scope and
     needs explicit confirmation before touching `velite.config.ts`.
3. Do not silently pick one and do not edit `velite.config.ts` yourself without
   that confirmation.

## Verification command

From the `ai-assets-directory` folder:

```bash
npx velite
```

This parses every file in `content/` against its collection schema and fails
loudly on a bad or missing frontmatter field. Run it after writing or editing
any article and report the result — don't claim the article is done without
running it.

## Humanizer pass (mandatory)

Read the full `humanizer` skill (`~/.claude/skills/humanizer/SKILL.md`, every
section — a grep for a few trigger words is not a pass) and apply it to the
draft before considering it finished. This is an existing project convention,
not specific to this skill: every new `content/learn` article and every edit
gets a full humanizer pass.
